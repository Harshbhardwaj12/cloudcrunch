# 10-Minute Demo Script

**Before you present (5 min earlier):**
- Run `python scripts/deploy.py` (or confirm the stack exists) — status badge shows **● API connected**.
- Open 4 browser tabs: ① the web app ② S3 input bucket ③ S3 output bucket ④ CloudWatch log group `/aws/lambda/image-processing-ImageProcessingFunction`.
- Have 2 test images ready: a big phone photo (3–8 MB JPEG) and a PNG with transparency.
- Process one image once beforehand so Lambda is "warm" (avoids a cold start delay on stage).

---

### 0:00 – 1:00 · Problem & objective
> "Phone photos are 3–8 MB. Serving them as-is wastes storage and bandwidth. Normally
> you'd run a server 24/7 to resize them. Our goal: process images automatically in
> the cloud **without running any server at all**."

### 1:00 – 3:00 · Architecture
Show the diagram in `README.md`. Walk the arrows:
> "The browser gets a secure, 15-minute presigned upload from API Gateway, uploads
> straight into the **input bucket**. That upload *is* the event — S3 triggers
> **Lambda**, which runs our Python + Pillow code, writes the result to the **output
> bucket**, and the app picks it up. Everything here is defined in one SAM template."

Mention: output bucket has no trigger → **no infinite loop**.

### 3:00 – 5:00 · Live upload
In tab ①: drop the big JPEG. Point out the file size/dimensions shown.
Choose **1024px · WebP · quality 75** → **Process in the cloud**.
Narrate the pipeline cards lighting up: API Gateway → S3 input → Lambda → S3 output.

### 5:00 – 7:00 · Behind the scenes
- Tab ②: refresh → `uploads/<jobId>/photo.jpg` is there (original, MB-sized).
- Tab ④: newest log stream → "New upload…", options, "Done…" with timings.
  > "Lambda ran only for these few hundred milliseconds — that's all we pay for."
- Tab ③: `processed/<jobId>.webp` and `results/<jobId>.json`.

### 7:00 – 9:00 · Results
Back to tab ①: drag the **before/after slider** — visually identical, file is ~95 % smaller.
Read the stats cards (original vs processed, % saved, dimensions). Click **Download**.
Then quickly run the transparent PNG → **JPEG 512px** to show format conversion
(and transparency flattened onto white). Point at the **session table**.

### 9:00 – 10:00 · Why serverless
- **Scalability:** 100 uploads at once = 100 parallel Lambdas, no config change.
- **Pay-per-use:** zero cost when idle; fits in the Free Tier.
- **Managed:** no OS patching; CloudWatch monitoring + error alarm built in.
- **Security:** private buckets, least-privilege IAM, presigned URLs with size/type limits.

> "Thank you — happy to take questions."

---

### Likely viva questions
| Question | Answer |
|---|---|
| Why two buckets? | Separation + prevents the processed file from re-triggering Lambda (infinite loop) |
| How does Lambda get Pillow? | Packaged as a Lambda **Layer** compiled for Amazon Linux / Python 3.12 |
| How does the browser upload without AWS keys? | Presigned POST generated by the API Lambda; expires in 15 min; S3 enforces ≤10 MB and image type |
| What's a cold start? | First invocation after idle loads the runtime + layer (~1 s); later ones are warm |
| How does it scale? | Lambda creates more concurrent instances automatically (default account limit 1000) |
| How are options passed to the processor? | As S3 object metadata (`x-amz-meta-max-size`, etc.), signed into the upload policy |
| How do you monitor failures? | CloudWatch Logs + Errors alarm; failures are written to `results/<id>.json` so the UI shows them |
| How is it deployed? | Infrastructure as Code — AWS SAM template, `sam deploy` via `scripts/deploy.py` |
